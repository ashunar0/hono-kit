# Rules

The rules every file keeps. Lint stops most of them; the rest are here.

- **Time**: a handler takes `now` from `c.get("now")`; nothing reads the clock (`hnk/no-clock-outside-app-entry`). A thing's times (`createdAt`, `updatedAt`) come from `now` too; a DB default is only for columns the app does not show
- **currentUser**: the guard in the endpoint's `auth` (required) reads the session and sets `c.var.currentUser`. The type checks it: a middleware whose Variables have no `currentUser` (one that only loads something and lets everyone through) cannot be `auth`, nor can an untyped one (`createMiddleware(async (c, next) => ...)` with no type argument). `requireAuth` sets the signed-in `CurrentUser`, `allowAnonymous` sets `null`. The guards are the app's (`src/middleware/auth.ts`: `requireAuth`, `allowAnonymous`, and what the app adds, such as `requireRole(...)` once its users have roles); reading the session is one function in deps (`sessionUser(headers)`), so every guard calls the same one and tests swap it in `makeDeps`. Write both for your auth stack. Until `sessionUser` reads its session (the template's returns `null`), every `requireAuth` endpoint answers 401 when called by hand (`wrangler dev`, curl); tests still sign in, since `appAs` swaps `sessionUser`. Other middleware goes in `middleware` and runs after `auth`
  - What a `CurrentUser` holds is the app's: what the auth provider gives with the session (the template: id, name, email). The app's own data about a person (a profile, a member) is a table of its own, read where it is needed. For a public endpoint that shows the signed-in a little more (their own drafts, whether they liked it), write a guard that lets everyone through and sets `currentUser` to `CurrentUser | null`; do not add another name (`viewer`)
  - **Permissions come in two kinds.** Decided by the role alone (only an admin adds a member): the guard, `auth: requireRole("admin")` (the template has no roles; add `role` to `CurrentUser` and the guard). Needs the row, or mixes in an "or" (an admin or the author): all of it in code, after the row is read, returning `err(Forbidden.code)`. Never put half of an "or" in the guard: it would turn away the other half. So `grep` of the guards lists who may call each endpoint
- **Failures**: expected ones (not found, no permission, an external service not answering) are returned as `Result` (`err(NotFound.code)`). Unexpected ones (the DB is down) are thrown
  - 401, 403, 404 are hono-kit standards (`Unauthorized` / `Forbidden` / `NotFound`). Make the others as `{ code, kind, message } as const`, and hono-kit decides the status from `kind`
  - **Details**: when the client needs the numbers behind a failure to show it (the budget and what was spent, the stock left), add `details: z.object({ ... })` to it. That failure is then always returned as `{ code, details }`: the function that found it returns `err({ code: OverBudget.code, details: { budget, spent } })`, and the handler passes it on as it is (`reply.failure(result.error)`). The response is `{ error: { code, message, details } }`, and the client's type knows the shape of `details` once it has checked the `code`. Do not make the client read the numbers again in another request: they may have changed, and it would repeat the rule. A failure that declares details cannot be thrown with `fail()`
  - `conflict` (409): it clashes with the thing's current state (taken, already sent, out of stock, a newer version). `unprocessable` (422): the request itself breaks a rule, whatever the state (past the deadline, outside opening hours). A rule of the clock is 422 even when waiting would let it pass: reading again does not change the answer
  - Name a code `<THING>_` + what happened (`INVOICE_NOT_SENDABLE`). A name the docs give is the API's contract: use it as is
  - Clients branch on the `code`, not on 403 / 409 / 422. When a business failure could be more than one kind, make it `conflict` and move on
  - What you cannot see is `NOT_FOUND` (its existence is not revealed); what you can see but may not touch is `FORBIDDEN`
- **Check order**: the guard (401 signed out → 403 a role that may not) → input validation 400 (schema) → NOT_FOUND → FORBIDDEN (a permission that needs the row) → unprocessable → conflict. The guard's 403 does not depend on the ID, so it reveals nothing
- **IDs**: `as …Id` is written only in the file that declares that `…Id` (its maker, `userId(value)`). Everywhere else calls the maker (`hnk/no-id-cast`)
- **Unique constraints**: the table's `uniqueIndex` decides, never a check you wrote first (two requests can interleave). Wrap the `insert` / `update` in `try/catch`; `uniqueViolationOf(error)` from `hono-kit/sqlite` returns the column it hit (`"members.email"`) or null. Turn each column into its own conflict `Failure`, and rethrow on null. So every column the docs call unique gets its own `uniqueIndex`
- **Returning**: `reply.success(body)` and `reply.failure(code)` (`reply.failure({ code, details })` for a failure that declares details). Neither takes a status: success is always 200 (`hnk/route-responds-200`), a failure gets its status from its kind. Create and update return the thing as its GET shows it; delete returns `{ ok: true }`. To return a file as it is (an R2 object, an upload), declare `200: file()` and return `reply.success({ body, contentType })`; `contentType` defaults to `application/octet-stream`, and other headers (`Cache-Control`) go on `c.header()`. A CSV or a page made from the data is not a file: list it as a format under 200 next to the JSON (`"text/csv": (list: List) => toCsv(list)`, [resources.md](resources.md)), so one endpoint answers both. To send people elsewhere, declare `303: redirect()` and return `reply.redirect(location)`: always 303, and only to a path of this app unless the declaration names the origin (`redirect({ origins: ["https://accounts.google.com"] })`). Anything else throws, so a `next` from the query cannot send people to another site
- **Lists**: a paged list uses these parts (whether a list is paged is up to the app): routes use `pageQuerySchema(filters)` / `pageResponseSchema(item)` / `pageResponse(page, map)` from `hono-kit`. The read takes a `PageQuery`, reads `limit + 1` rows and returns `toPage(...)` from `hono-kit/page`. The cursor compares with `lt` for a newest-first list and `gt` for an oldest-first one
- **Module scope**: keep no changing values there (`let`, a `Map`, an array you push to). One Worker serves concurrent requests, so it would be shared across them (`hnk/no-module-scope-state`). A dummy in tests that collects what was sent takes its array from the test
- **Optional input**: `undefined` in input, `null` in the DB. Normalize with `?? null` before writing
- **Tests**: use the real local D1. HTTP via `request(user, method, path, body, at)` from `test/fixtures.ts`; pass `at` whenever the answer depends on the date. D1 is shared by the tests in a file, so a test that reads a list uses its own user (`someone()`), not `alice`

## Do not

- Edit `node_modules/hono-kit`. If something is missing, tell the user
- Copy libs or helpers into the project
- Scatter failure codes as strings (take them from a `Failure` or a hono-kit standard)
